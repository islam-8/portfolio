Abstract
This monograph presents the design, architectural analysis, and algorithmic implementations of a low-latency administrative database core developed exclusively within standard ISO C99. Due to strict constraints forbidding dynamic runtime object layers, virtual tables, or Garbage Collection interfaces, the system adopts a nested, sequential heap allocation topology. We explore the memory footprint characteristics of managing nested structures containing linked records without incurring double-allocation hazards or fragmentation. A double-pass iterative walking algorithm guarantees $O(1)$ stack utilization during memory reclamation and achieves deterministic zero-leak performance validated through Valgrind profile tools. Our empirical results demonstrate predictable CLI state machine operation under nested dynamic constraints.

I. Architectural Principles & Memory Layout

In low-resource, high-reliability applications, such as bare-metal embedded clinical systems or safety-critical monitoring hardware, the presence of runtime environments (e.g., dynamic garbage collectors or managed runtime engines) introduces non-deterministic pauses. To mitigate this jitter, we propose a database architecture engineered from first principles using standard ISO C99. The core design mandates direct control over memory boundaries, structures, and pointer manipulation.

The fundamental challenge of mapping heterogeneous relational data in C99 is the absence of native dynamic collections. While static arrays offer simple $O(1)$ index access, they introduce compile-time upper boundaries. In clinical systems, exceeding these boundaries causes catastrophic heap or stack overflows. To address this limitation, our engine employs a nested singly-linked list topology, allowing the dynamic footprint of the system to scale proportionally with physical memory capacity.

To maintain strict data integrity without class isolation barriers, the database enforces role-based access control (RBAC)[1]. Access validation is achieved using low-level string comparison operations (`strcmp()`) compiled into read-only flash space. By matching string hashes against compiled constant arrays, the application safely segregates read-only views (User Mode) from mutable, schema-altering write transactions (Admin Mode).

II. Nested Structural Data Models

The relational link between a unique Patient entity and an arbitrary, dynamic sequence of scheduled appointments is traditionally modeled via foreign key indexes. In our pure C implementation, this relation is modeled directly in physical RAM by nesting pointers. A primary node (`struct Patient`) contains its corresponding identity, static metadata, and an offset boundary pointer mapping to the head of a secondary singly-linked chain composed of `struct Appointment` nodes.

Figure 1: High-precision Heap memory mapping of `struct Patient` and its nested dynamic relation with `struct Appointment` nodes showing padding margins.

A critical architectural benefit of this approach is data locality. By executing separate allocations (`malloc`) for parent nodes and nested nodes, we prevent memory footprint stagnation. Memory blocks are instantiated only upon request. However, this raises the challenge of structural alignment and byte-padding in memory[2]. On modern 32-bit and 64-bit hardware, compilers silently inject padding bytes to align structure fields with 4 or 8-byte word boundaries. Our layout design strictly sequences the fields—ordering large arrays first followed by primitive variables—to reduce padding waste and keep structure sizes optimized.

III. Algorithmic Deallocation & Leak Prevention

While nested allocations offer flexible layouts, they present a significant hazard during deletion or application shutdown. In standard C, executing a simple `free()` operation on a primary node (`Patient*`) only deallocates the continuous memory block allocated for the parent structure. The child nodes (`Appointment*`) linked inside its structure become orphaned in the Heap region, causing memory leaks that gradually consume the target system's resources.

To achieve robust zero-leak performance, our engine implements a strict Double-Pass Destructor Sweep algorithm. When the system initiates the deallocation of a Patient record, it prevents direct parent destruction by executing the following linear sequence:

Figure 2: Logical sequence of the Double-Pass Destructor Sweep ensuring zero dangling references in the Heap region.

First, the program caches the starting pointer of the nested list (`appointments`). It then traverses this list sequentially, storing each successor node's pointer before freeing the current node. This prevents the loss of head references during deallocation. Once the nested chain is completely cleared, the destructor executes Pass 2, deallocating the parent node's memory allocation and safely re-linking the main list boundaries. By verifying this mechanism with the Valgrind Leak Analyzer, the engine consistently achieves "All heaps freed — zero leak errors" under every run.

IV. Security Boundaries & Overflow Mitigation

In traditional C-based architectures, string inputs are vulnerable to buffer overflow attacks (e.g., Stack or Heap Smashing), where input size exceeds structure field capacity. This vulnerability often arises when using unsafe library utilities like `gets()` or `strcpy()`, which do not validate destination buffers.

To safeguard our system, the database engine implements strict security boundaries. Field storage arrays, such as `char name[50]` and `char diagnosis[100]`, are guarded during runtime ingestion. All input operations utilize standard `fgets()`, which enforces a strict size parameter limit. By intercepting raw input buffers and stripping stray trailing newline indicators (`\n`), the system prevents buffer overflows, securing execution boundaries on any C99 standard library target.
